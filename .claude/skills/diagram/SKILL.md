# 図の作成を依頼されたとき

手順の本体はリポジトリの `kit/DIAGRAMS.md`（Copilot のキットと同じ手引き）。最初に全部読み、その 1〜6 章の順に進める。ここには、このリポジトリで作業するときの差分だけを書く。

## 最初の回答

この時点では図を作成しない。`kit/DIAGRAMS.md` の 1 章のとおり、理解した内容・作成する図の案（1 枚 1 テーマ）・質問（回答で図が変わるものだけ、最大 5 つ、仮の前提つき）を示す。資料から十分に分かる 1 枚の図なら、作成してから確認してよい。

## 作業フォルダ

- 依頼ごとに `work/<依頼の短い名前>/` を作り、`DESIGN.md`（設計メモ）と図の記述 `01-〇〇.yaml` … を保存する。`work/` はリポジトリに含めない（.gitignore）。
- 実在の顧客データ（実 IP、実ホスト名、顧客名など）は `work/` の外に書かない。リポジトリは公開しているので、`examples/` には架空のごく簡単なものだけを入れる。

## 生成と確認

- テンプレート：`examples/patterns/{overview,process,network,compare}.yaml` をコピーして始める（キットでは `pattern-〇〇.yaml`）。
- 生成して PNG にする：`npm run preview -- work/<名前>/*.yaml`。`.drawio` は記述と同じフォルダ、PNG は `out/work/<名前>/` の下に出力される（draw.io 公式の描画処理）。
- 指摘は 0 件にする。PNG は必ず開いて確認する（`kit/DIAGRAMS.md` 6 章の確認観点）。
- 図の文字と回答の文章は、`kit/DIAGRAMS.md` の「言葉づかい」に従う。

## 納品

`.drawio` と PNG のパス、設計メモ、仮定した事項・未確定事項の一覧を短く示す。修正したい箇所を聞く。

## ツールで表現できないとき

パターンに合わない図や、ツールで描けない表現（たとえば線を枠の特定の辺から出したい）に当たったら、記述でごまかさず、何が足りないかを利用者に伝える。ツールを修正するなら `AGENTS.md` の確認ループに従う。
