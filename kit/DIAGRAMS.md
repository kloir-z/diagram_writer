# 作図の手引き

依頼と資料から、diagrams.net で編集できる構成図（`.drawio`）を作成する手順。
あなたが決めるのは「誰に、何を説明する図か」と、図の記述（YAML）の内容。座標・寸法・線の経路・色は dw.js が決める。

手順は次の 6 段階。どの段階も省略しない。

1. 依頼を受けたら：資料を読む → 理解した内容をまとめる → 質問する
2. 設計メモを書く
3. パターンを選ぶ（テンプレートから始める）
4. 図の記述を書く
5. 生成 → 機械チェック → 修正
6. PNG で確認して修正し、納品する

---

## 1. 依頼を受けたら：資料を読む → 理解した内容をまとめる → 質問する

資料を最後まで読んでから、最初の回答で次の 3 つを示す。この時点では図を作成しない。

1. 理解した内容（2〜3 行）。何についての図を、誰に、何のために作るか。
2. 作成する図の案。1 枚につき 1 テーマ。図ごとに「誰に、何を説明する図か」とパターン（3 章）を 1 行で書く。
3. 質問。回答によって図が変わるものだけを、最大 5 つまで。選択肢と、回答が無い場合の仮の前提を添える。

### 質問すること（回答で図が変わるもの）

| 観点 | 例 | 何が変わるか |
|---|---|---|
| 読者と使う場面 | 上長への説明、顧客との打ち合わせで投影、申請書に添付 | 詳しさ、用語、図の枚数 |
| いちばん伝えたいこと | 「承認までは本番を変更しない」「外部への通信は 1 本だけ」 | タイトル、太くする線、補足 |
| 範囲 | どこまで描くか、描かないもの（既存部分、保守経路など） | 載せる要素 |
| 資料の食い違い・不足 | 構成図と表でアドレスが違う、接続先の記載が無い | 質問するか、未確定事項にするか |
| パターンごとの確認（下の表） | | |

| パターン | 確認すること |
|---|---|
| 全体像 | 拠点・区画の分け方／同じ機器をまとめて台数で示してよいか（「サーバ ×6」）／図で追う流れ（1 本） |
| 工程 | 起点と終点／人の作業とシステムの処理の境目／止める箇所（承認・確認）と、その前後の違い／記録・通知 |
| 接続と境界 | 区画とアドレス／どれが FW か／通信の開始側とポート／許可しない通信／VPN・専用線 |
| 比較 | 比べる 2 つ（現状と目標、案 A と案 B）／なくなるもの・増えるもの・変わらないもの／移行の時期 |

### 質問しないこと

- 資料に書いてあること。資料から読み取れることは、読み取った内容を書いて先に進める。
- dw.js が決めること（色、配置、線の経路、文字の大きさ）。
- 好みの細部。まず作成して示し、修正したい箇所を聞く方が早い。

### 回答が無い・「任せる」の場合

仮の前提で進め、納品時に仮定した事項を一覧で示す。図が 1 枚で資料から十分に分かる場合は、質問せずに作成してから確認してよい（この場合も仮定した事項を示す）。

## 2. 設計メモを書く

図を書く前に、設計メモ（`DESIGN.md`）を書く。図を修正するときも、まずメモと図が合っているかを確認する。

```markdown
# 設計メモ：〇〇

## 読者と伝えたいこと
- 読者：〇〇
- 伝えたいこと：〇〇（一文）

## 図の一覧
| 図 | 誰に、何を説明するか | パターン | 配置（grid のスケッチ） | 太くするもの |
|---|---|---|---|---|
| 01 全体像 | 上長：どこに何があり、どうつながるか | 全体像 | [本社, DC, クラウド] / [本社, DC, 取引先] | 注文の流れ |

## 構成の前提（資料から読み取ったこと・仮定した事項）
- 〇〇

## 未確定事項
- 〇〇（誰に確認するか）
```

## 3. パターンを選ぶ（テンプレートから始める）

図はたいてい次の 4 つのパターンのどれかになる。パターンに合ったテンプレートをコピーし、内容を書き換えるところから始める。テンプレートは機械チェックの指摘が 0 件で、見た目も確認済み（キットでは `pattern-〇〇.yaml`、リポジトリでは `examples/patterns/〇〇.yaml`）。

| パターン | 説明すること | 配置 | テンプレート |
|---|---|---|---|
| 全体像 | どこに何があり、どうつながるか | 拠点・区画を枠にし、図で追う流れが左から右へ読めるように grid で並べる。枠の中は上から下へ | `pattern-overview.yaml` |
| 工程 | 誰が何をどの順に行い、どこで止めるか | 段階を列にして左から右へ。手順は要素にして番号（①…）を付ける。承認と変更の線だけ太く | `pattern-process.yaml` |
| 接続と境界 | どの通信を許可するか | 拠点 → 区画（アドレス）→ 機器の入れ子。外部への通信は FW を経由して描き、ポート番号を線のラベルにする | `pattern-network.yaml` |
| 比較 | 何が変わり、何が残るか | 変更前と変更後（案 A と案 B）を同じ並びで左右に配置し、間を太い矢印（`transition`）で結ぶ | `pattern-compare.yaml` |

パターンごとの決まりは次のとおり。

- 全体像：図で追う流れ（依頼・データ・操作の流れ）を 1 本決め、それが一方向に読めるように grid を決める。同じ種類の機器はまとめて台数で示す（「L3 スイッチ ×2」）。線のラベルは目的（「注文を登録」「推論」）。
- 工程：段階の枠の見出しには「承認前：確認のみ」のように、その段階で何をして何をしないかを書く。手順の番号は要素の見出しに付け（「③ 差分を確認」）、担当は `sub` に書く。対象（本番機器など）は下の段に 1 つ配置し、読み取りだけの線（`data`）と変更する線（`device`、太く）を分ける。
- 接続と境界：区画は `zone` にしてアドレスを `specs` に書く。外部への通信は「送信元 → FW」（`dir: none`、ラベルに「HTTPS 443 → 宛先」）と「FW → 宛先」に分け、FW の補足に許可する通信を書く。許可しない通信は `blocked`。
- 比較：左右の枠の中は同じ並びにする（同じものが同じ高さに並ぶ）。なくなるもの・増えるものは補足で示す。移行の矢印は 1 本だけ。

5 つ目のパターン「物理配線図」（機器のポートとケーブル）は、物理構成モデル（`INSTRUCTIONS.md` の後半）から生成する仕組みを準備中。

## 4. 図の記述を書く

1 ファイル = 1 枚。座標は書かない。次は、そのまま生成できる最小の例（各項目の意味は下の表）。

```yaml
title: 受注システム：注文は本社の PC から Web サーバに入る
subtitle: 前提・例の説明を書く。架空なら「（架空の例）」
direction: down          # 枠の中の流れの向き：down（上から下）か right（左から右）
grid:                    # おおまかな配置。行ごとに最上位の要素の id を並べる。「.」は空き
  - [office, dc]         # 同じ id を隣り合うマスに書くと、その範囲にまたがる
nodes:
  - id: office           # 英数字と . _ -。図全体で一意
    label: 本社
    kind: site
    tone: internal
    children:
      - { id: pc, label: 業務 PC, kind: pc, sub: ブラウザ }
  - id: dc
    label: データセンター
    kind: site
    tone: internal
    grid: [[web, ap]]    # 枠の中も grid で並べられる（grid で並べた枠の中だけ）
    children:
      - { id: web, label: Web サーバ, kind: server, sub: 受注画面, specs: 198.51.100.10 }
      - { id: ap, label: AP サーバ, kind: server, specs: 198.51.100.70 }
edges:
  - { from: pc, to: web, class: user, label: 注文を登録 }
  - { from: web, to: ap, class: flow }
notes:
  - { to: ap, text: "補足は 2 行まで\n未確定事項・注意" }
```

### 要素（nodes）

| 項目 | 書くこと |
|---|---|
| `label` | 名前。短く（1 行 15 字ほど） |
| `sub` | 役割・製品・担当（灰色の小さい字） |
| `specs` | 識別子：IP、アドレス帯、型番、台数の内訳（等幅の字） |
| `kind` | 種類。色が決まる（下の表） |
| `tone` | 枠の色分け：`internal`（自社）・`customer`（顧客）・`restricted`（制限区画）・`neutral`（外部・その他） |
| `children` | 子要素。子要素のある要素は枠になる |
| `grid` | 枠の中の配置 |
| `emphasis` | 太枠で強調（1 枚に 1〜2 か所まで） |
| `layer` | 流れの向きの段をそろえる（0 始まり）。通常は不要 |

| `kind`（要素） | 凡例の名前（色） |
|---|---|
| `person` `pc` | 利用者・端末（灰） |
| `server` `vm` `storage` | サーバー・仮想マシン（青） |
| `gpu` `llm` `ai-service` | AI（GPU・LLM）（紫）。クラウドの LLM もこれにし、どこにあるかは枠で示す |
| `tool` `service` | 自動化・ツール（緑） |
| `repo` `data` | データ・リポジトリ（橙） |
| `switch` `router` | ネットワーク機器（黄） |
| `firewall` `jump` | セキュリティ境界（赤） |
| `cloud` | 外部のサービス（白） |
| `other` | その他 |

| `kind`（枠） | 使いどころ |
|---|---|
| `site` | 拠点・会社・大きな区切り（実線の太枠。`tone` で色） |
| `zone` | 区画・セグメント（破線。`tone` で色。凡例に意味が載る） |
| `host` | 1 台の機器の中（その機器で動くもの） |
| `rack` `cluster` | ラック、クラスター |
| `group` | 単なるまとまり（薄い破線）。工程の段階など |

### 線（edges）

| `class` | 凡例の名前 | 使いどころ |
|---|---|---|
| `user` | 人の操作・やりとり | 人の操作、人への表示 |
| `flow` | 処理の流れ（依頼・呼び出し） | システム間の依頼・呼び出し、工程の順序 |
| `build` | 開発・構築（作成・修正） | 開発者・開発ツールによる作成・修正（破線） |
| `llm` | LLM API（推論） | LLM の呼び出し |
| `tool` | ツール呼び出し | エージェントによるツールの呼び出し |
| `device` | 機器操作（SSH・API） | 機器へのログイン・設定変更 |
| `vpn` | VPN・拠点間接続 | 拠点間の VPN・専用線 |
| `data` | データ・ログの流れ | データの受け渡し、読み取りだけのアクセス（破線） |
| `approval` | 承認 | 人による承認 |
| `blocked` | 通信させない | 許可しない通信・経路を作らない通信（× 付きの点線） |
| `transition` | 移行（時期・段階） | 比較パターンの、変更前から変更後への移行（太い矢印） |

- `label`：目的（「注文を登録」）か、プロトコルとポート（「SSH 22」「HTTPS 443 → Claude API」）。2 行まで。
- `step: 3`：ラベルの先頭に ③ を付ける（手順を線で表すとき）。工程パターンでは、番号を要素の見出しに付ける方が読みやすい。
- `dir`：`forward`（既定）・`both`（双方向）・`none`（矢じり無し。FW までの線など）。
- `emphasis: true`：太くする（1 枚に 1〜2 本まで。いちばん伝えたいことを示す線だけ）。
- 枠（子要素のある要素）も線の端にできる（「開発元 DC を構築・修正」）。包含関係にある要素同士は線でつながない。

### grid の決まり

- 図の `grid` には最上位の要素を、枠の `grid` にはその枠の子要素を、すべて配置する。
- 同じ id を隣り合うマスに書くとまたがる（長方形に限る）。「.」は空き。
- 同じ行・列の枠は上端・左端がそろう。大きさの近い枠はマスいっぱいに広がり、要素の少ない枠は広がらない。
- 空きマスだけの行（列）があると、またがる枠の分はそこが伸びる（例：`[[customer, internet], [customer, .]]` なら、インターネットの枠は上の行の高さのまま）。
- `grid` が無い図は、つながりに沿って全体を 1 回で配置する（小さな図向き）。

### 書き方の決まり

- **1 枚 1 テーマ**。要素 40・線 60 を超えたら分ける（機械チェックが警告する）。
- タイトルは「テーマ：結論」。副題に前提と「（架空の例）」などを書く。
- 名前は資料の表記のまま（機器名・ポート名を翻訳しない）。説明の言葉は短い日本語（体言止め）。
- 補足（`notes`）は 2 行まで。未確定事項・注意・前提に使う。補足は対象の右（`direction: right` なら下）に付く。中を grid で並べた枠には付けられない。
- 実在の顧客データを、このリポジトリやキットのサンプルに書かない。

### 言葉づかい

図の文字と設計メモは、IT の設計書で普通に使う言葉で書く。英語の言い回しの直訳や比喩は使わず、実際の物と操作を名指す（「通信が外に出る」ではなく「外部へ通信する」）。

次の言葉と書き方は、Qiita の技術記事を生成 AI の前後で比べた計測で、AI 以後に大きく増えたもの。使わない。

<!-- textlint-disable ai-words-ja/no-ai-words -->

| 避ける | 代わりに |
|---|---|
| 道具 | ツール、製品名 |
| 置く | 配置する、記載する、保存する |
| 要点 | 伝えたいこと、結論 |
| 入口、出入口 | 実物の名前（ポート、接続先、最初に読むファイル） |
| 実測 | 計測、測った値 |
| 〜の正は（source of truth の訳） | 正式な定義は〜、〜を基準にする |
| 効く | 効果がある、役に立つ |
| 静かに壊れる、黙って捨てる | エラーを出さずに失敗する、知らせずに捨てる |
| 別物 | 違う、別の |
| 土台、骨格、受け皿、導線 | 基盤、構成、保存先、手順 |
| 太字の見出しとコロンで始まる箇条書き（`- **項目**：説明`） | 見出しの無い文、表 |
| 述語の後のコロンで一覧やコードを続ける（`次のとおりです：`） | 「次のとおり。」で文を終える |

## 5. 生成 → 機械チェック → 修正

- キット（Copilot のコード実行環境）：`python run.py preview 図.yaml --out-dir out`。`out/` に `.drawio` と確認用の PNG が出力される（PNG は dw.js が独自に描いたもので、細部は draw.io と少し違う。成果物の本体は `.drawio`）。PNG が不要なときは `build`。
- リポジトリ：`npm run preview -- 図.yaml`。`.drawio` は記述と同じフォルダ、PNG は `out/` の下（draw.io 公式の描画処理）。

出力の 1 行目は要約（大きさ・占有率・線の交差・指摘の数）。指摘は 0 件にする。

| 指摘 | 主な修正方法 |
|---|---|
| エラー（YAML・項目名・参照） | 行番号の箇所を修正する。id の綴り、grid に子要素が全部あるか、包含関係にある要素同士の線 |
| 横長すぎる／縦長すぎる | grid の行と列を入れ替える。枠の中の `direction` を変える。図を分ける |
| 配線の問題：間隔が狭い／経路が無い | 線の両端が近くなるよう grid を変える。間に挟まる枠をずらす。要素を減らす |
| 線が関係のない枠を通る／要素を貫通 | 同上。つながる要素同士を隣のマスにする |
| 線が枠の見出しを横切る | 見出しを短くする。線の接続先を枠の下側に配置する |
| 線のラベルが要素・見出し・線に重なる、ラベル同士が重なる | ラベルを短くする（2 行に分ける）。同じ 2 つの要素の間の線をまとめる |
| 線どうしが重なる | 同じ 2 つの要素の間の線をまとめる（ラベルを 2 行に）。片方の端を別の要素にする |
| 矢じりの直前で曲がる | 両端の要素の並びを変える（たいてい grid の変更で解消する） |
| 線の交差が多い（要約の数） | 図で追う流れの順に grid を並べ直す。交差する線の端を入れ替える |

占有率（要約）は、向きや配置を変えた案を比べる目安。大きいほど余白が少ない。

---

## 6. PNG で確認して修正し、納品する

PNG で次を確認する。修正したら 5 に戻る。2〜3 回で収まらなければ、パターンや図の分け方を見直す。

1. タイトルと図だけで、5 秒でテーマが分かるか（設計メモの「伝えたいこと」がすぐ読み取れるか）。
2. 流れが一方向に読めるか。行ったり来たりしていないか。
3. 線：迂回・細かい折れ曲がり・どの線のラベルか分かりにくい箇所が無いか。
4. 余白：要素の少ない大きな枠、空いた列や行が無いか。16:9 の資料に収まる縦横比か。
5. 色・線種：凡例の意味と使い方が合っているか（人の操作に `flow` を使っていないか、など）。
6. 内容：資料と食い違いが無いか。仮定した事項が確定事項のように書かれていないか。

納品物：

- `.drawio`（diagrams.net で開いて編集できる）と PNG
- 設計メモ（`DESIGN.md`）
- 仮定した事項と未確定事項の一覧（資料のどこを根拠にしたか）
